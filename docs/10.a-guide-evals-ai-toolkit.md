# Guide: Running LLM Evals Locally in VS Code (AI Toolkit / Foundry Toolkit)

[← Back to README](../README.md) | [Prerequisites & Setup](01-prerequisites-and-setup.md) | [Architecture Overview](02-architecture-overview.md) | [Foundry portal eval variant →](10.b-guide-evals-foundry.md)

This guide walks you through running **offline LLM evaluations** against the agents in this app from inside **VS Code**, using the **Foundry Toolkit** extension (formerly known as "AI Toolkit"). You'll point the Toolkit at the sample dataset shipped with the repo (`evals/thomas-the-turtle-eval.jsonl`), pick a few built-in evaluators (Coherence, Fluency, Similarity, plus a custom "moral honored" evaluator), and read the per-row + aggregate scores — all without leaving your editor.

> **Local vs cloud evals.** This guide uses the in-VS Code experience, which is great for fast iteration on a prompt or model change. Once you're ready to run evals on the deployed Foundry-hosted agents — including continuous evaluation against production traces — see the companion guide [Running Cloud Evals in Microsoft Foundry](10.b-guide-evals-foundry.md). Both guides use the same JSONL dataset schema, so anything you build here is reusable there.

> **Heads-up on naming.** Microsoft renamed the "AI Toolkit for VS Code" extension to "Foundry Toolkit" in 2025. The older name is still in wide use, including in this repo's title. The extension publisher and ID (`ms-windows-ai-studio.windows-ai-studio`) are unchanged, so just install the latest version — wherever this guide says "Foundry Toolkit", it's the same extension.

## What you'll build

After completing this guide you'll have:

- The **Foundry Toolkit** extension installed and connected to your Azure OpenAI / Microsoft Foundry deployment as the **judging model**.
- A standalone evaluation job that scores `evals/thomas-the-turtle-eval.jsonl` against the built-in **Coherence**, **Fluency**, and **Similarity** evaluators.
- A custom **"Moral Honored"** LLM-based evaluator that returns a 1–5 score plus reasoning for whether the agent's `response` actually delivers on the user-supplied moral lesson.
- Aggregate scores in the Toolkit's evaluation results view, with the option to drill into any single row.

This is pure local tooling — no code changes to the app, no Foundry portal interaction, no cost beyond the judging-model tokens.

---

## Why eval locally first?

The Foundry portal has a richer evaluation experience (continuous evals, agent targets, scheduled runs) and that's covered in [10.b](10.b-guide-evals-foundry.md). But the in-editor flow shines when:

- **You're tweaking a prompt** and want to know within seconds whether your change made `OrchestratorAgent` outputs more coherent.
- **You haven't deployed yet.** Local evals don't require any provisioned agents — they score whatever `query` → `response` pairs you've put in the JSONL.
- **You want to keep the loop in version control.** The dataset is just a file in `evals/`. You can add rows, commit them, and let teammates run the same eval locally.

Treat local evals as **unit tests for prompts** and the portal evals (10.b) as **integration tests for agents**.

## Before you start

Make sure you have:

- This repo cloned and the app at least partially set up (you don't need it actually running). See [Prerequisites & Setup](01-prerequisites-and-setup.md) if you haven't already.
- **VS Code 1.92** or newer.
- An **Azure OpenAI** or **Microsoft Foundry** model deployment you can use as the judging model. The same `gpt-5.4` (or whatever you've configured in `backend/.env` as `FOUNDRY_MODEL_DEPLOYMENT_NAME`) works fine — judging models don't need to differ from the model under test for AI-assisted scores like Coherence/Fluency.
- The repo's sample dataset `evals/thomas-the-turtle-eval.jsonl` (already in the repo).

You do **not** need to have completed [Guide 09: Foundry-Hosted Agents](09-guide-foundry-hosted-agents.md) for this guide.

## Step 1 — Install Foundry Toolkit and connect a model

1. In VS Code, open the **Extensions** view (`Cmd+Shift+X` / `Ctrl+Shift+X`) and search for **Foundry Toolkit** (publisher: Microsoft). Click **Install**.

2. Open the Foundry Toolkit view from the activity bar (the **Foundry Toolkit** icon).

3. Under **MY MODELS**, click **+** to add your Azure OpenAI / Foundry deployment:

   - **Model source:** *Azure AI Foundry* (or *Azure OpenAI* if your subscription is configured that way — both work).
   - **Endpoint:** the same value as `FOUNDRY_PROJECT_ENDPOINT` in your `backend/.env` (the short account-level form, e.g. `https://<account>.services.ai.azure.com/`).
   - **Deployment name:** the same value as `FOUNDRY_MODEL_DEPLOYMENT_NAME` in your `backend/.env` (e.g. `gpt-5.4`).
   - **Authentication:** *Microsoft Entra ID* (Toolkit will pop a sign-in if needed). Don't paste an API key here — `DefaultAzureCredential` is the preferred path for everything in this repo.

4. Once the model appears in the **MY MODELS** list, click it and run a quick **Try it** chat to confirm it works.

> **Tip:** If you've already configured `az login` for the rest of this repo, the Toolkit's Entra ID flow should pick up your token without any extra steps.

## Step 2 — Inspect the sample dataset

Open `evals/thomas-the-turtle-eval.jsonl` from the repo root. Each row is a single JSON object with these fields (all of which the Foundry Toolkit understands by name):

| Field | Purpose |
|---|---|
| `query` | The prompt that was sent to the agent (verbatim — what you'd see in `prompts.py` + the user's form data). |
| `ground_truth` | The "good" answer used as a reference for similarity-style metrics. For the orchestrator this is a JSON-stringified `StoryOutline`; for the architect it's the rendered story text. |
| `response` | The agent's actual output that we're scoring. Captured from a real run of the app. |
| `tool_calls` | Empty for this app — none of our chat agents use function-calling. Kept in the schema so the dataset is forward-compatible. |
| `tool_definitions` | Same — empty. |

The repo ships with **2 hand-curated rows** (one for `OrchestratorAgent`, one for `StoryArchitectAgent`) so you can see end-to-end results immediately. The "[Optional — Grow the dataset](#optional--grow-the-dataset-from-a-real-story-run)" section below shows how to add more rows from real generation runs.

> **Why JSONL?** The Toolkit (and the Foundry portal) both expect one JSON object per line. Don't be tempted to wrap the file in a top-level `[ ... ]` array — that won't load.

## Step 3 — Create a standalone evaluation

1. In the Foundry Toolkit view, expand **TOOLS** in the left pane and click **Evaluation** to open the Evaluation view.

2. Click **Create Evaluation** in the toolbar.

3. Fill in the **Create Evaluation** form:

   - **Evaluation job name:** e.g. `thomas-baseline`.
   - **Evaluator:** for a first run, multi-select **Coherence**, **Fluency**, and **Similarity**. (We'll add a custom evaluator in Step 5.)
   - **Judging model:** select the model you registered in Step 1 (`gpt-5.4`). All three of these evaluators are AI-assisted, so they need a judging model.
   - **Dataset:** click **Import JSONL** and pick `evals/thomas-the-turtle-eval.jsonl` from the repo. The Toolkit will preview the first row on the right.

4. Click **Create**. The job opens in a new editor tab.

5. Verify the column mapping in the top of the job tab — `query`, `response`, and `ground_truth` should all be auto-mapped to the corresponding columns in your dataset. (For Similarity, both `response` and `ground_truth` are required.)

6. Click **Run Evaluation**.

The Toolkit calls the judging model once per (row × evaluator) pair, so a 2-row × 3-evaluator run is 6 model calls — usually a few seconds plus model latency.

---

## Step 4 — Read the results

When the run finishes, the job tab shows a **results table**:

- One column per evaluator (Coherence, Fluency, Similarity), one row per dataset row.
- Each cell holds a score (typically **1–5** for the AI-assisted evaluators), plus a per-cell **reason** if you hover or expand the cell.
- An **aggregate row** at the bottom averages each column.

What to look for in this app's outputs:

- **Coherence** scores below 4 on the orchestrator row usually mean the JSON outline has logical jumps (e.g. characters introduced in plot summary that don't appear in `character_descriptions`). Skim the `response` to confirm.
- **Fluency** is typically high for our prompts because the architect's output is full natural-language pages — if it dips, look for stilted transitions or run-on sentences.
- **Similarity** is the noisiest of the three for creative writing — a perfectly fine response can score low simply because the wording diverges from `ground_truth`. Use it as a directional signal, not a hard pass/fail.

If you want a tabular spreadsheet view, click **Open In Data Wrangler** in the toolbar (requires the Data Wrangler extension).

## Step 5 — Add a custom evaluator

The built-in evaluators don't know what a "moral lesson" is, so they can't directly tell you whether the architect's story actually delivers on the user-supplied moral. Let's add one that does.

1. In the Evaluation view, switch to the **Evaluators** tab and click **Create Evaluator**.

2. Fill in the form:

   - **Name:** `Moral Honored`
   - **Description:** `Whether the generated story actually delivers on the user-supplied moral lesson.`
   - **Type:** *LLM-based*

3. Paste this prompt:

   ```text
   You are reviewing a children's storybook output produced by an AI agent.

   The original prompt embedded a "moral of the story" that the agent was asked
   to honor. The agent's response is a multi-page story. Your job is to score how
   faithfully the story embodies that moral — through the protagonist's actions,
   the way the conflict is resolved, and any closing reflection — for a 5-to-8
   year-old reader.

   Original prompt (contains the requested moral):
   {{query}}

   Agent's response (the story to evaluate):
   {{response}}

   Score from 1 to 5:
     1 = the moral is absent or contradicted by the resolution.
     2 = the moral is mentioned but not lived out in the plot.
     3 = the moral is partially supported by the protagonist's behaviour.
     4 = the moral is clearly demonstrated through the action and resolution.
     5 = the moral is the emotional centre of the story; a child would absorb it without needing it spelled out.

   Respond with ONLY a single JSON object on one line, no Markdown fences:
   {"score": <integer 1-5>, "reason": "<one short sentence explaining the score>"}
   ```

4. Click **Save**.

5. Re-run the evaluation (or create a new one) with **Moral Honored** added to the evaluators list. A new column appears in the results table.

> **Why a 1–5 scale?** Matches the built-in evaluators so an aggregated dashboard view feels consistent. The Toolkit's parser treats the `score` field as the comparable metric and the `reason` as displayed text; if you change the schema, the parser may not know how to summarize it.

If you want a **code-based evaluator** instead (e.g. count moral keywords, verify page count matches `target_pages`), pick *Code-based (Python)* in the create form — the Toolkit scaffolds a function with a fixed `(query, response, **kwargs)` signature for you to fill in.

## Optional — Grow the dataset from a real story run

The repo ships with 2 rows. Add more by running the app and capturing the agent's actual `query` / `response` pairs:

1. Run the app locally (`./start-app.sh` or follow the [Local Quickstart](00-local-quickstart.md)).

2. Generate a story through the UI. Open the **Network** tab in your browser dev tools and watch the SSE stream from `POST /api/generate-story`. Each agent emits a `prompt_sent` and a `response_received` event you can scrape.

   - **Lower-friction option:** add a small print statement in the agent of interest (`backend/app/agents/orchestrator.py` etc.) right after `result = await run_structured(...)` to dump `prompt` and `result.text` to a file you can grep.

3. For each captured pair, append a JSON line to `evals/thomas-the-turtle-eval.jsonl`:

   ```json
   {"query": "<the prompt>", "ground_truth": "<your hand-curated 'good' answer>", "response": "<the agent's actual answer>", "tool_calls": [], "tool_definitions": []}
   ```

   The `ground_truth` field is what makes Similarity work; if you don't care about that evaluator, you can leave it as an empty string and just stick to Coherence + Fluency + your custom evaluators.

4. Re-run your evaluation in the Toolkit — it picks up the new rows automatically.

> **Where to keep big datasets?** Keep small, hand-curated regression sets (5–20 rows) checked into `evals/`. Larger generated datasets (hundreds of rows from production traces) belong in the Foundry portal — see [10.b](10.b-guide-evals-foundry.md) for the trace-capture workflow.

## Troubleshooting

**"No model selected as judging model"** → The evaluators you picked are AI-assisted (Coherence/Fluency/Similarity/your LLM-based custom). Either select a judging model or swap to a code-based evaluator (e.g. F1 Score, BLEU, METEOR — none of these need a judge).

**"Authentication failed" or 401** when the judge model runs → Run `az login` in a terminal, then click the model in **MY MODELS** and re-test it. The Toolkit caches the token; if it's stale, removing and re-adding the model picks up a fresh one.

**Dataset preview is empty / "Could not parse JSONL"** → Each line of `evals/thomas-the-turtle-eval.jsonl` must be a single self-contained JSON object. If you opened the file and reformatted it with Prettier, undo that — JSONL is line-oriented, not pretty-printable. The repo's checked-in version is correct.

**Similarity scores are all very low even on obviously-good rows** → Similarity is a literal-overlap-aware metric; for highly creative outputs it's expected to be middling. Check that your `ground_truth` field actually contains text comparable to `response` (same agent, same JSON shape, same kind of prose). If the ground truth is empty or shaped totally differently (e.g. a JSON object compared to plain prose), the evaluator has nothing to anchor on.

**"Rate limit exceeded" from the judge model** → Some Foundry deployments have aggressive per-minute quotas. Either lower the dataset row count for the run or raise the deployment's TPM limit in the Foundry portal.

**Custom evaluator returns "could not parse score"** → Double-check the prompt instructs the judge to emit ONLY a single-line JSON object (no Markdown fences, no preamble). Models trained on chat sometimes wrap JSON in ```` ``` ```` blocks even when told not to; if that keeps happening, change `Respond with ONLY a single JSON object` to `Respond with valid JSON. Do NOT wrap it in Markdown fences.`
