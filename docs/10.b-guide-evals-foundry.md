# Guide: Running Cloud Evals on Foundry-Hosted Agents (Microsoft Foundry portal)

[← Back to README](../README.md) | [Prerequisites & Setup](01-prerequisites-and-setup.md) | [Foundry-Hosted Agents](09-guide-foundry-hosted-agents.md) | [← AI Toolkit eval variant](10.a-guide-evals-ai-toolkit.md)

This guide walks you through running **LLM evaluations in the Microsoft Foundry portal** against the agents you provisioned in [Guide 09: Hosting the Agents in Microsoft Foundry](09-guide-foundry-hosted-agents.md). Unlike the in-editor Foundry Toolkit experience ([10.a](10.a-guide-evals-ai-toolkit.md)), portal evals can target **the live, deployed Foundry agent** as the system under test — so you're scoring exactly what your users (and your continuous-eval pipeline) will see.

> **You must complete [Guide 09](09-guide-foundry-hosted-agents.md) first.** This guide assumes the 10 agents have been provisioned (via `python -m app.scripts.provision_foundry_agents`) and that you've at least once successfully run the app with `AGENT_HOSTING_MODE=foundry`.

## What you'll build

After completing this guide you'll have:

- A **named evaluation run** in the Foundry portal targeting one of your provisioned agents (e.g. `OrchestratorAgent`).
- A scored result set across the built-in **Coherence**, **Fluency**, and **Similarity** evaluators, plus a custom **Moral Honored** prompt evaluator.
- (Optional) A **continuous evaluation** that re-runs the dataset against the agent on a schedule, surfacing regressions in the Foundry monitoring dashboard.
- (Optional) A CI-friendly Python snippet using `azure-ai-evaluation` that runs the same eval and exits non-zero on regressions.

---

## Why portal evals (vs. local)?

| Capability | Local (10.a) | Portal (10.b) |
|---|---|---|
| Score `query`/`response` rows you've already captured | ✅ | ✅ |
| Score the **live deployed agent** end-to-end (the portal calls the agent for you) | ❌ | ✅ |
| Compare across agent **versions** | manual | first-class |
| Continuous eval (scheduled runs against production traces) | ❌ | ✅ |
| Surface scores in monitoring dashboards | ❌ | ✅ |
| Iterate on prompts in seconds while in your editor | ✅ | slower |

A good rhythm:
- Use **10.a (local)** while you're tweaking a prompt in `prompts.py` for fast feedback.
- Run **10.b (portal)** after `provision_foundry_agents` pushes the prompt to Foundry, so you have an authoritative score on the deployed version.

## Source-of-truth refresher

This is the most important thing to internalize before clicking around the portal:

> **In `foundry` mode, the agent definition deployed in your Foundry project is the source of truth — NOT `prompts.py`.**

Concretely: if you edit `ORCHESTRATOR_INSTRUCTIONS` in `prompts.py` but don't re-run the provisioning script, the next portal evaluation against `OrchestratorAgent` will score the **old** prompt. Likewise, edits made in the Foundry portal's prompt editor will be silently overwritten the next time someone runs the provisioning script.

The provisioning script is the **only** sync point between the two. See the ["Source-of-truth contract"](09-guide-foundry-hosted-agents.md#source-of-truth-contract-read-this) section in Guide 09 for the long version.

## Before you start

You need:

- The 10 agents provisioned in your Foundry project. Verify with:
  ```bash
  cd backend
  python -m app.scripts.provision_foundry_agents
  ```
  All 10 should report `ok`. If anything is `duplicate`, `model-drift`, or `error`, fix that before continuing — eval results against an ambiguous lookup are meaningless.
- The **Foundry User** role (formerly "Azure AI User") on the Foundry project. The deployment Bicep grants this to the container app's managed identity, but for portal-driven evals **your own user identity** also needs it. Ask whoever provisioned the project to add you under **Project settings → Access control (IAM)** if it isn't already there.
- An Azure OpenAI / Foundry **chat-completion deployment** that can serve as the **judging model** for AI-assisted evaluators (Coherence, Fluency, Similarity, custom prompt-based). Reusing the same `gpt-5.4` deployment used by the agents is fine.
- The repo's sample dataset `evals/thomas-the-turtle-eval.jsonl` (already in the repo).

## Step 1 — Open the Evaluation page

1. Sign in to [https://ai.azure.com](https://ai.azure.com) and select your project (the one that holds your provisioned agents — e.g. `sofio-eus2-foundry`).
2. In the left navigation pane, click **Evaluation**.
3. Click **+ Create**.

> Alternatively: navigate to **Agents** → click `OrchestratorAgent` → **Evaluation** tab → **Create**. This pre-fills the agent target for you.

---

## Step 2 — Choose Agent as the evaluation target

In the **Create evaluation** wizard:

1. **Target type:** select **Agent**.
2. **Agent:** pick the agent you want to score. For this app's workflow the most interesting starting target is **`OrchestratorAgent`** (because its `StoryOutlineDraft` output drives every downstream agent), but you can repeat this guide for any of the 10 agents in [Guide 09's "The 10 hosted agents"](09-guide-foundry-hosted-agents.md#the-10-hosted-agents) section.
3. **Agent version:** leave at *Latest* unless you're A/B-comparing two specific versions (more on that in [Step 5](#step-5--run-and-read-results)).

> **Why "Agent" and not "Dataset"?** Targeting *Agent* tells the portal to **call the live hosted agent** for each row's `query`, then evaluate the agent's actual response. If you instead choose *Dataset*, the portal scores the pre-captured `response` field as-is — useful for offline regression but doesn't exercise the deployed agent.

---

## Step 3 — Provide the dataset

The wizard offers three dataset paths:

### Option A — Upload the repo's JSONL (recommended starting point)

1. Click **+ Add dataset → Upload from local**.
2. Pick `evals/thomas-the-turtle-eval.jsonl` from the repo.
3. The portal previews the rows on the right.
4. **Column mapping** (important):
   - Map `query` → **agent input** (the user message that will be sent to the hosted agent).
   - Map `ground_truth` → **ground truth** (used by Similarity).
   - Leave `response` unmapped — the portal will overwrite it with the live agent's actual response when the run executes.
   - Leave `tool_calls` / `tool_definitions` unmapped (none of this app's chat agents use function-calling).

> **Note on system prompts in agent-target mode.** Because `OrchestratorAgent` is hosted in Foundry, its system prompt is baked into the agent definition (`PromptAgentDefinition.instructions`). The portal does NOT let you override it at eval time — and that's by design, per the source-of-truth contract. If you want to score a different prompt, save the agent as a new **version** first, then re-run the eval against that version.

### Option B — Synthetic dataset generation

If you want to grow the dataset, use **Synthetic dataset generation**. Provide:
- A reference prompt describing the kind of inputs to generate (e.g. *"Children's-story outline requests in the format used by the OrchestratorAgent in this project — see evals/thomas-the-turtle-eval.jsonl for the shape."*)
- The number of rows.
- Optionally upload a couple of example rows to anchor the style.

This is a great way to build a 50-row regression set without hand-writing each one.

### Option C — Capture from traces

The richest source of `query`/`response` data is your **own production runs**. Once your app is calling Foundry-hosted agents, every invocation is captured as a trace:

1. In the dataset selector, choose **From traces**.
2. Filter by agent (`OrchestratorAgent`), time range, and (optionally) any custom span attributes.
3. Click **Save as evaluation dataset**.

You'll typically pair this with [Optional — Continuous evaluation](#optional--continuous-evaluation-against-production-traces) below.

---

## Step 4 — Pick evaluators

For a first run, multi-select:

- **Coherence** — does the response hang together logically? Most useful for `OrchestratorAgent` (does the outline make narrative sense?) and `StoryArchitectAgent` (do pages flow into each other?).
- **Fluency** — is the language natural for a 5–8 year-old reader? Most useful for `StoryArchitectAgent`, `LookAndFindActivityAgent`, `CharacterGlossaryAgent`, `StorySuggestionAgent`.
- **Similarity** — token-overlap with `ground_truth`. Useful as a directional signal for the orchestrator (whose ground-truth is a structured `StoryOutline`); noisier for the architect's prose.

For each AI-assisted evaluator the portal will ask you to pick a **judging model** — point it at the same `gpt-5.4` deployment you've been using throughout the app.

> **For the reviewer agents** (`PerPageReviewerAgent`, `CoverReviewerAgent`, etc.), the more interesting evaluators are **Task Adherence** and **Task Completion** from the [agent-evaluators](https://learn.microsoft.com/en-us/azure/ai-foundry/concepts/evaluation-evaluators/agent-evaluators) family — they're tuned to score whether an agent followed its instructions. Add those alongside the general-purpose ones once you're ready to evaluate beyond the orchestrator.

---

## Step 5 — Run and read results

1. Click **Create + Run**. The portal queues the evaluation; for a 2-row × 4-evaluator run against a hosted agent it usually completes in under a minute.
2. When it finishes, the **Run details** page shows:
   - **Aggregate scores** per evaluator at the top.
   - **Per-row breakdown** below — click any row to expand the agent's actual `response` (in agent-target mode this is the **live** response, not the pre-captured one) along with each evaluator's per-row score and reasoning.
   - **Failures** column if any rows errored (e.g. content-filter blocks). Click through for the underlying error.

To compare prompt versions:

1. Tweak the prompt locally, push with `python -m app.scripts.provision_foundry_agents`. The script will report `updated` for the agent whose instructions changed.
2. Back in the portal, navigate to **Agents → `OrchestratorAgent` → Versions** to confirm the new version is listed.
3. Re-run your evaluation, but in Step 2 set **Agent version** to the new version number explicitly.
4. Use the **Compare** button on the Evaluation list to view the two runs side-by-side.

## Step 6 — Add a custom prompt-based evaluator

The built-in evaluators don't know what a "moral lesson" is. Let's add the same **Moral Honored** evaluator from the [local guide](10.a-guide-evals-ai-toolkit.md#step-5--add-a-custom-evaluator), this time as a portal-managed evaluator usable across the project.

1. Navigate to **Evaluation → Evaluators → + Create new evaluator**.
2. **Type:** *Prompt-based* (the portal's name for what the Toolkit calls "LLM-based").
3. **Name:** `Moral Honored`.
4. **Prompt template:**

   ```text
   You are reviewing a children's storybook output produced by a Microsoft
   Foundry-hosted agent (OrchestratorAgent or StoryArchitectAgent).

   The original prompt embedded a "moral of the story" that the agent was asked
   to honor. The agent's response is either a structured outline or a multi-page
   story. Your job is to score how faithfully the response embodies that moral —
   through the protagonist's actions, the way the conflict is resolved, and any
   closing reflection — for a 5-to-8 year-old reader.

   Original prompt (contains the requested moral):
   {{query}}

   Agent's response:
   {{response}}

   Score from 1 to 5:
     1 = the moral is absent or contradicted by the resolution.
     2 = the moral is mentioned but not lived out.
     3 = the moral is partially supported by the protagonist's behaviour.
     4 = the moral is clearly demonstrated through the action and resolution.
     5 = the moral is the emotional centre of the response; a child would absorb it without needing it spelled out.

   Respond with ONLY a single JSON object on one line, no Markdown fences:
   {"score": <integer 1-5>, "reason": "<one short sentence explaining the score>"}
   ```

5. **Output schema:** declare `score` (integer) and `reason` (string). The portal uses this to surface scores in dashboards and to compute aggregates correctly.
6. **Save**, then re-run your evaluation with `Moral Honored` selected in Step 4.

The new evaluator is now reusable across runs and across agent targets — perfect for treating "honors the moral" as a project-wide quality bar.

## Optional — Continuous evaluation against production traces

The static dataset eval is great for regression-testing prompt changes. **Continuous evaluation** flips the model: every time the agent is invoked in production, the run is auto-evaluated and the scores feed back into the monitoring dashboard. This is how you catch quality regressions that don't show up in your hand-curated dataset.

1. Connect an **Application Insights** resource to your Foundry project under **Monitoring → Application analytics** (one-time setup).
2. In **Evaluation → Continuous Evaluations**, click **Create**.
3. **Target:** `OrchestratorAgent` (and repeat for any other agent you want monitored).
4. **Sampling:** start with a low rate (e.g. 5% of invocations) to keep judge-model costs manageable.
5. **Evaluators:** the same set you used in Step 4, plus your `Moral Honored` evaluator.
6. **Schedule / trigger:** *On every traced invocation* (default) or a periodic schedule.

Once active, the **Monitoring → Application analytics** dashboard will start charting `coherence`, `fluency`, `similarity`, and `moral_honored` over time, broken down by agent. A sustained drop on any chart is your early-warning signal for a prompt regression — usually **before** you'd notice it from user complaints.

> **Cost tip.** Each evaluated invocation uses N judge-model tokens, where N scales with the size of `query` + `response`. For a story-generation app that can mean ~15-20k tokens per evaluated run. Start with low sampling, watch your token spend in Cost Management for a week, then dial in a sustainable rate.

For full setup details see the [Foundry continuous evaluation docs](https://learn.microsoft.com/en-us/azure/ai-foundry/concepts/observability).

## Optional — Run evals from CI with the Foundry SDK

For a CI-friendly evaluation that fails the build on regressions, use the [`azure-ai-evaluation`](https://pypi.org/project/azure-ai-evaluation/) package. The shape is roughly:

```python
# scripts/run_orchestrator_eval.py
import os
import sys

from azure.ai.evaluation import (
    AIAgentConverter,
    CoherenceEvaluator,
    FluencyEvaluator,
    SimilarityEvaluator,
    evaluate,
)
from azure.ai.projects import AIProjectClient
from azure.identity import DefaultAzureCredential


PROJECT_ENDPOINT = os.environ["FOUNDRY_PROJECT_ENDPOINT"].rstrip("/") \
    + "/api/projects/" + os.environ["FOUNDRY_PROJECT_NAME"]
JUDGE_MODEL = os.environ["FOUNDRY_MODEL_DEPLOYMENT_NAME"]


def main() -> int:
    credential = DefaultAzureCredential()
    project = AIProjectClient(endpoint=PROJECT_ENDPOINT, credential=credential)

    # Resolve the latest version of the orchestrator agent.
    agent = next(a for a in project.agents.list() if a.name == "OrchestratorAgent")

    judge_config = {
        "azure_endpoint": os.environ["FOUNDRY_PROJECT_ENDPOINT"],
        "azure_deployment": JUDGE_MODEL,
        "credential": credential,
    }

    result = evaluate(
        data="evals/thomas-the-turtle-eval.jsonl",
        target=AIAgentConverter(agent),  # "live agent" target
        evaluators={
            "coherence": CoherenceEvaluator(model_config=judge_config),
            "fluency": FluencyEvaluator(model_config=judge_config),
            "similarity": SimilarityEvaluator(model_config=judge_config),
        },
        output_path="eval_results.json",
    )

    metrics = result["metrics"]
    print(metrics)
    # Fail the build if average coherence drops below 4.0
    if metrics.get("coherence.coherence", 0) < 4.0:
        return 1
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

Wire this into your CI workflow on every prompt change. The `result["studio_url"]` field returned by `evaluate(...)` deep-links straight to the run in the portal so reviewers can drill in without needing to re-run.

> The `azure-ai-evaluation` package is **not** included in this repo's `requirements.txt` because it's only needed for CI scripts, not the runtime app. Add it to your CI image's separate requirements file.

## Troubleshooting

**"Forbidden — Foundry User role required"** when opening Evaluation → Create → Agent → the agent picker is empty → Your account needs **Foundry User** (formerly "Azure AI User") on the project. Get it added under **Project settings → Access control (IAM)**. The container app's managed identity has it; you also need it for portal-driven actions.

**Agent target shows "no agents available"** → Either you haven't run the provisioning script (see [Guide 09 Step 1](09-guide-foundry-hosted-agents.md#step-1--provision-the-agents)), or you're looking at the wrong project. Confirm the URL bar in the portal matches `FOUNDRY_PROJECT_NAME` from your `backend/.env`.

**Eval run errors with "agent: response_format mismatch"** → The agent's deployed JSON schema is older than the Pydantic model in `app/models.py`. Re-run `python -m app.scripts.provision_foundry_agents` (or `--recreate` if instructions also changed) to push the latest schema, then retry the eval.

**Eval row failed with `400: content_filter`** → Azure OpenAI's content filters can flag legitimate inputs (especially "race" themes, conflict descriptions, etc.). This is unrelated to your prompt design. Either remove the offending row from the dataset, or follow the [content-filter customization docs](https://learn.microsoft.com/en-us/azure/ai-services/openai/how-to/content-filters) to relax the policy on your deployment.

**Similarity scores look very low even on obviously-good rows** → This metric is overlap-sensitive; for highly creative outputs it's expected to be middling. Either use BLEU/F1/METEOR (which are also overlap-sensitive but normalize differently) or de-emphasize Similarity in your aggregate score and lean on Coherence + your custom `Moral Honored` evaluator instead.

**Continuous eval costs are exploding** → Each evaluated invocation re-runs every selected evaluator on the full `query` + `response` payload. Lower the sampling rate, drop the noisier evaluators (Similarity especially), and consider scoring only a single agent (`OrchestratorAgent`) rather than every agent in the workflow.

**"My prompt edits in Foundry portal disappeared"** → Someone re-ran `python -m app.scripts.provision_foundry_agents` and the script's `_decide_action` saw drift between the portal and `prompts.py` (which it considers source-of-truth) and pushed a new version overwriting your portal edits. This is by design — see the [source-of-truth contract](09-guide-foundry-hosted-agents.md#source-of-truth-contract-read-this). If you want to keep portal edits, also update `prompts.py` to match.
